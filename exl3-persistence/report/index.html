A write-behind disk tier for vLLM's KV-offload connector

An enhancement to vLLM's v1 offloading connector, plus a node-local NVMe backend for it, running GLM-5.3-Flash on four DGX Sparks. Long-running agent sessions survive eviction and come back in seconds instead of minutes of prefill, from a disk tier an order of magnitude larger than GPU memory. The tier costs nothing while the engine is idle or unpressured, and about five percent of decode only while the cache is full and evicting. That five percent buys back the most expensive work the server does.

1 · What this is

vLLM's v1 KV-offload connector ships with a CPU tier: blocks are copied out of GPU memory on the request path and looked up on the next request. This work extends that connector in two layers, and the split matters for anyone who wants to reuse it:

  • In the engine: write-behind semantics for the connector. Twelve patches against upstream vLLM at commit 83252ea899, 705 lines added and 480 removed across eight files, almost all inside kv_connector/v1/offloading/ and v1/kv_offload/, with one hook each in the block pool and the scheduler. They add: stores driven by prefix-cache eviction instead of by requests, a pressure gate so an idle engine writes nothing, an idle-time flusher for stale content, an in-memory durable-key index so misses are free, and drained fail-soft outcomes so a failed transfer becomes a cache miss rather than an assertion. Nothing here is disk-specific.
  • Out of tree: a node-local NVMe backend. The recipe_persistence package (about 4,800 lines) implements the connector's OffloadingSpec for per-rank local disk: an immutable checksummed object store with a bounded sqlite index, per-rank coordinators with an authenticated metadata endpoint, and the geometry and transfer handlers. It installs over dist-packages and ships by rsync plus restart, with no engine rebuild.

Configuration is a handful of PERSIST_* environment knobs. The serving configuration is otherwise the published TP4 playbook, unchanged.

Why it matters most on Sparks, and why it is not Spark-specific. On a DGX Spark the model weights and the KV pool share one unified memory, so the pool is a fraction of what a discrete-GPU box gets for the same model, eviction pressure arrives early, and every byte moved on the request path competes with prefill and decode for the same memory bandwidth. A write-behind design that touches nothing on the request path is therefore worth more here than anywhere. But the connector changes know nothing about GB10, EXL3 or this model: they apply to any model vLLM serves through the v1 offload connector, and the NVMe backend is a drop-in OffloadingSpec for any node with local disk.

2 · Why: agents and bots hold sessions for hours

Agentic and bot workloads look nothing like chat. A coding agent, a research loop, or a monitoring bot builds a context of 100k to 400k tokens over an hour or more, goes quiet while tools run or a human reads, and then comes back. On a shared engine that pause is fatal to the cache: other traffic evicts the session, and the next turn pays a full prefill. At 200k tokens that is 112 seconds of the server's most expensive work, repeated every time the session is touched after a gap.

The GPU pool on this fleet holds 3.39M tokens, which is a handful of such sessions. The disk tier changes the arithmetic in two ways:

  • Rehydration skips prefill. An evicted session comes back at NVMe speed. The 200k session above returns in 3.0 s instead of 112 s; the engine spends those seconds copying bytes, not recomputing attention.
  • The cache is large enough to keep everything. A 1 TB quota per rank is about 44M token-equivalents: hundreds of long sessions can stay warm on disk at once, so a bot fleet's whole working set fits rather than a lucky few sessions.

Sessions under 32k prompt tokens skip the disk tier by design. Small contexts recompute faster than a disk scan costs, so short-context bots pay nothing and get nothing, and the tier's budget is spent where prefill is actually expensive.

3 · How: write behind, only under pressure

The tier never touches the request path. The GPU prefix cache decides what is worth keeping, and the disk only ever receives what the GPU is about to throw away.

background copies
Deferred-free sinkheld, not freed Evicted blocks are held outside the free queue while a background copy drains them to disk. Under allocation pressure the sink declines new holds and hands blocks back, so it can never stall the scheduler.
→NVMe, per rank
sqlite index
Disk tier1 TB per rank Immutable checksummed objects, one store per rank, restored on demand straight back into the GPU pool. Namespace-fingerprinted to the model, quant, template and layout.

Four properties make this cost nothing when it is not needed:

  1. Writes happen on eviction, never on a request. Nothing is offered, held or admitted while a prompt is being served. Store bytes on the request path measure zero at every context size.
  2. An idle engine writes nothing. A free-pool watermark gates the sink: while the pool has headroom, holds are declined and no copy runs. The only measured cost, decode −4.6%, appears when the pool is full and copies are draining, which is exactly the situation in which sessions are being lost.
  3. Stale content is flushed in idle time. Cache content untouched for an hour (configurable) is copied to disk during decode-free steps only, in place and fenced against reuse. A decode step never pays for durability, by construction, and a long-quiet session is safe on disk before anything evicts it.
  4. A miss costs a set lookup, not a disk scan. An in-memory index of durable keys answers negatives on all four ranks without touching sqlite, so the lookup that sits on the scheduler's critical path adds nothing measurable to prefill.
Why five percent is the right price. The pressure tax only exists while sessions are being evicted, and each evicted long session that later returns would otherwise cost a full prefill. On the measured numbers, one avoided 200k rehydration saves about 109 s of prefill compute, which is the same server time as roughly 40 minutes of decode at −4.6%. That is arithmetic on the measurements above, not a separate measurement, but the direction is not close: the tax is paid in the moments it is cheapest and repaid in the moments prefill is dearest.

4.2 The pressure gate, isolated

With the gate active, an idle engine running an 8k + 64k smoke wrote zero bytes (census: zero new objects) at 1,984 / 1,987 prefill tok/s and 50–51 decode tok/s, persistence-off parity with nothing moving. Under a 120 × 9k flood with interleaved decode streams, decode measured 39.1 vs 41.0 tok/s idle (−4.6%). That is the entire pressure tax. The idle flusher separately lands stale content at 2–4 MB/s in the background (4.62 GB in a 36-minute run), and the restore path reads those bytes back.

4.3 Overflow and restore

400 unique 9k sessions (3.6M tokens) pushed through the 3.39M-token pool, then an early session re-requested while the engine was still busy:

The tier stores exactly what the GPU evicted rather than whole-prompt copies, so a restore transfers only the blocks that were actually lost. At 9k the recompute alternative is a few seconds; the ratio grows with session size, which is why the 200k case is the one that matters for agents.

4.4 Standard benchmark and production smoke

Local Inference Labs standard bench (C1–C6, 700-token outputs, salted prompts): 38.3 / 73.4 / 51.6 / 52.9 / 64.3 / 69.2 aggregate tok/s, zero failures, within variance of the published no-persistence baseline.

Agentic ladder, 300-token outputs, tier live: 32k → 15.4 s TTFT at 2,030 prefill tok/s; 128k → 66.6 s, 2,008; 256k → 141 s, 1,897; 400k (404,745 tokens, the largest single request this fleet has served) → 261 s, 1,549 tok/s, decode healthy. A 4 × 32k concurrent burst ran clean. The practical single-request ceiling is about 405k tokens; the configured 850k maximum is refused at admission in 1.1 s. We believe that ceiling is a property of this serving recipe on unified memory (weights, drafter and pool sharing 121.7 GiB per node), not of the offload connector: the connector adds no per-request memory. The same ladder with persistence off has not been run to confirm it, and should be.

5 · Limits, stated plainly

  • Cold restore of a large session after a restart is not yet whole. Disk restore is proven at 9k (1.42 s) and as a 423,936-token partial inside a live 800k prefill; cache retrieval is proven at 200k (3.0 s). A complete 200k+ session restored cold from disk after a restart still recomputes today: under a heavy flood the bounded capture window (4,096 held blocks, 8 keys per step) lands gigabytes rather than the whole evicted set. The dials exist (eviction_hold_cap, eviction_store_per_step, idle_flush_per_scan) and both directions of the mechanism are proven; whole- session coverage at flood scale is engineering, not architecture. Until it lands, quote disk restore at the tested sizes.
  • The store is tested to 78.8 GB per rank. Its eviction watermarks near the 1 TB quota have not been exercised at scale.
  • Sessions under 32k tokens are never persisted. This is deliberate, and the gate is a single knob if a workload wants it lower.
  • The ~405k single-request ceiling is attributed to the recipe on unified memory, not to the connector, on reasoning rather than a persistence-off measurement of the same ladder.
  • Deep-context decode under pressure (256k, −13%) is the one cell in §4.1 that a longer soak should firm up before it is quoted as settled.
