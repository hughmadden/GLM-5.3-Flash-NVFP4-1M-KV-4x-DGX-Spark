Request cap, disk KV persistence, and cache-hit accounting

GLM-5.3-Flash EXL3 4bpw at TP4 on 4× DGX Spark (GB10), DFlash2 speculative decoding, with a node-local disk KV tier. Two defects found and fixed, the standard bench that frames them, and an open restore-path defect that hangs clients behind a metric reading 0.0%.
GLM-5.3-Flash 320B MoE EXL3 TR3 4bpw 4× DGX Spark (GB10) vLLM TP=4, 121.7 GiB UMA/node DFlash2 k=7 node-local disk KV tier 2026-09-11

TL;DR

This is the sequel to the two-Spark disk-KV report. The same idea (park a long agent session on the node's own disk instead of recomputing its prefill) was moved onto four Sparks at tensor parallelism 4 with an EXL3 4-bit weight format. Getting there surfaced two defects that had nothing to do with the persistence design itself, plus one accounting gap that matters for anyone trying to operate the tier.

The recipe book: what to actually change

Five findings are load-bearing. Each is a one-line change with a measured consequence.

  1. Lower GPU_MEM_UTIL to 0.75 on a GB10 unified-memory node. vLLM sizes its KV pool from total device memory, not from what is free, so on unified memory it will happily commit the host out of existence. 0.85 killed the engine on any prefill above ~83k tokens; 0.75 survives 255k–404k tokens.
  2. Set VLLM_SPARSE_INDEXER_MAX_LOGITS_MB explicitly. The sparse-indexer profiling branch reserves max(32 × max_model_len × 4, cap × 1 MiB) bytes and drops the reference, but the caching allocator keeps the block reserved. With the default cap of 512 this was ~58% of all the headroom the engine had. Lowering MAX_MODEL_LEN would not have shrunk it.
  3. Do not give the KV store a durable commit per operation. The store is a reconstructible cache (kv_load_failure_policy=recompute), so synchronous=EXTRA bought nothing and cost a full fsync on every lease grant — 8.697 ms, on a path that runs every scheduler step. WAL + NORMAL gives 0.024 ms.
  4. Make durability an explicit, validated policy rather than a hard-coded pragma, and keep the library default unchanged so existing behaviour and tests still hold.
  5. Never trust exit code 0 from a GB10 engine. Every death in this campaign exited 0 with OOMKilled=false; the API server then hung draining the client socket. The real signals are the kernel's NVRM lines and /health.
  6. Size a per-step lookup budget against the longest prefix, not a round number. A RETRY that means "later" is destructive when the caller discards its progress on it. At ~110 tokens per chunk, a budget of 8 hangs any prefix over ~900 tokens.
  7. Make a throttle's release independent of the work it blocks. A gate advanced only by a scheduler hook that never runs for a deferred request is a deadlock, not a throttle.
  8. Gate every benchmark on clocks, under load. A GB10 can come back from a reboot pinned at 611–728 MHz instead of ~2,200 MHz with a zero throttle mask, which silently depresses every published number. Idle sampling proves nothing; the check must run while the GPU is busy.
Correction of record. An earlier internal note claimed the persistence fix recovered decode from ∼12 to 58.1 tok/s (a 4.8× win). That comparison was confounded: the two arms differed in speculative-decoding acceptance length, in whether a page-cache flusher was still running, and in leftover benchmark containers competing for the engine. A controlled re-run with the engine idle, the flusher stopped and 8 repetitions per arm gives 42.1 tok/s at ~83 ms/step with the fix reverted versus 41.0 tok/s at ~83 ms/step with the fix applied. The per-step latency did not change. There was no decode bug. The isolated durability result (8.697 → 0.024 ms per lease grant) is the real and sufficient reason to keep that fix. Section 3.4 explains the arithmetic that makes raw tok/s unsafe to compare across prompts.
The open finding, and the one to read first if you only read one. The disk tier's write path works: it accepts data, and 7 GB of it survived several engine restarts. Its read path does not. A controlled test stored one 8,171-token prefix as 112 chunks, then immediately re-requested it: the repeat never returned — 240 seconds, client-side timeout — and the counters added in this work show exactly why. The tier found the entire prefix, 112 chunks of 112, within two seconds, and then transferred zero bytes across the whole 240 s while the scheduler retried the lookup 36,137 times. The request sits in the deferred state with nothing running and nothing else queued, so there is no error, no timeout, and no client-visible signal. Meanwhile the engine correctly reports External prefix cache hit rate: 0.0%, which is complete and accurate accounting: the tier was consulted and did not serve. The combination is the dangerous part — clients hang while the metric says only "low hit rate". Section 5 has the reproduction and the verdict.

Two properties of this hardware dominate everything below. First, the GB10's memory is unified: the GPU and the host draw from one 121.69 GiB pool. A GPU allocator that sizes itself from total device memory is therefore also deciding the host's fate. Second, the modules are small enough that the weights, the KV pool, the draft model and the engine's host-side footprint all have to be reasoned about in the same budget. There is no second pool to spill into.

The persistence tier is a separate pure-Python package. It deliberately does not import torch or vLLM, so its whole store, eviction and lease machinery can be exercised by unit tests with dummy data and no engine at all. That design decision is what made both fixes in this report cheap to find (section 6).

2 · Defect 1: the request cap

2.1 Symptom

Large prefills killed the engine. The failure was not a clean rejection and not a container OOM. The sequence was identical every time:

  1. a prefill of roughly 83k–90k tokens, or larger;
  2. an NVIDIA driver allocation failure logged to the kernel as NVRM: ... Out of memory [NV_ERR_NO_MEMORY] ... _memdescAllocInternal;
  3. vLLM's own SIGTERM handler shutting the engine down;
  4. the process exiting 0 with OOMKilled=false;
  5. the API server staying alive but hanging while draining the client socket, so /health never returns and a manual down/up cycle is required.

Step 4 is the trap. Monitoring that keys on exit status or on container OOM sees nothing wrong.

2.2 Root cause: the memory budget was over-committed

Measured at GPU_MEM_UTIL=0.85 on a 121.69 GiB node:

2.3 The allocation that actually set the cap

The cap is not a vague over-commitment story. It is one named reservation. In vllm/model_executor/layers/sparse_attn_indexer_kpool.py, inside sparse_attn_indexer_kpool(), the memory-profiling branch does this:

# Reserve profiler-visible memory for the worst-case decode logits,
# whose shape is [B * next_n, max_model_len]. This profiling branch
# returns before invoking the logits kernel itself.
worst_decode_tokens = min(sched.max_num_seqs * (num_spec + 1),
                          sched.max_num_batched_tokens)
decode_logits_elems = worst_decode_tokens * max_model_len * 4
prefill_cap_elems   = envs.VLLM_SPARSE_INDEXER_MAX_LOGITS_MB * 1024 * 1024
max_logits_elems    = max(decode_logits_elems, prefill_cap_elems)
_ = torch.empty(max_logits_elems, dtype=torch.uint8, device=...)

With this configuration the two terms are:

termvalue
worst_decode_tokens = min(4 × (7+1), 7168)32
decode_logits_elems = 32 × 850000 × 4103.8 MiB
prefill_cap_elems = 512 × 1 MiB (the default cap is 512)512 MiB
max_logits_elems = max(103.8, 512)512 MiB

Two things follow, and both are counter-intuitive enough to be worth stating plainly.

  • The environment cap binds, not max_model_len. The max_model_len term only becomes the binding one above max_model_len ≈ 4.19 M. So lowering MAX_MODEL_LEN would have shrunk the KV pool and changed nothing about this buffer. The lever is VLLM_SPARSE_INDEXER_MAX_LOGITS_MB.
  • It is a reservation, not a live allocation. The result is assigned to _, so the reference is dropped immediately — but PyTorch's caching allocator keeps the block reserved, and the driver therefore still holds it. It is taken on first indexer use, which is the first prefill: exactly when the deaths happened.

2.4 What was ruled out

The sparse-indexer workspace is a separate, frequently-blamed allocation and it is not the culprit. It is closed-form in the config:

entries = min(max_num_seqs, MNBT) * cdiv(max_model_len + num_spec, compress_ratio)
        = min(4, 7168) * cdiv(850007, 4) = 4 * 212502 = 850,008 entries
bytes   = 850,008 * 132 B (128 fp8 + 4 B scale) + 1 MiB radix = 112.2 MiB

At 112.2 MiB it is also profile-time locked and subtracted from the KV pool, so it never competes with prefill transients. A patch that resizes this workspace does return 4,173 MiB to the pool, but the pool is preallocated: that helps throughput, not headroom.

2.5 Fix and validation

The fix is a configuration value: GPU_MEM_UTIL 0.85 → 0.75, plus an explicit VLLM_SPARSE_INDEXER_MAX_LOGITS_MB.

The post-fix state is itself diagnostic. The request now sits at num_requests_waiting_by_reason{reason="deferred"} = 1 with running = 0 — held by a KV-transfer constraint, not by memory. The memory death is gone and the next limit in line is non-fatal. That distinction matters, and section 5.3 shows why it is also not the whole story.

Trade-off, stated plainly. The GPU KV pool is about 12.5 GiB smaller, so fewer tokens stay resident on the GPU. That is a good trade here, because there is a disk tier to absorb the overflow: the cap fix is what makes the persistence tier earn its keep instead of being a liability. On a deployment without a second tier, the same change would simply mean more recompute.

3 · Defect 2: a durable fsync on every lease grant

3.1 Root cause

The store's lease path commits an INSERT with PRAGMA synchronous=EXTRA, and the cache-lookup path grants a lease through a synchronous coordinator RPC. Because on_schedule_end() runs every scheduler step, every step that touched a lease paid a full fsync.

operation (unit harness, dummy data, no engine)latency
lookup miss0.022 ms
lookup hit (lease granted)8.697 ms median / 11.39 ms p95

The engine metric agreed: vllm:kv_offload_lookup_sync_delay_seconds was consuming about 9.3 s of every 10 s window across roughly 800 lookups. The engine was blocked on persistence lookups for the large majority of wall-clock time.

The key judgement is that this store is a reconstructible cache, not a journal. Its configured load-failure policy is recompute: if a lease or payload is lost, the engine recomputes the prefill. So synchronous=EXTRA was buying a durability guarantee that the system had already decided it did not need, at the cost of an fsync per commit.

3.2 Fix: durability becomes an explicit policy

  1. Store takes journal_mode and synchronous as validated parameters. Defaults are unchanged (delete + extra), so the library contract and every pre-existing test still hold.
  2. Coordinator reads the two values from the spec's extra_config.
  3. Launcher renders them from PERSIST_SQLITE_JOURNAL_MODE / PERSIST_SQLITE_SYNCHRONOUS; this deployment sets wal + normal.
  4. Directory audit now permits the index.sqlite-wal and -shm files that WAL creates. This is worth calling out: the audit had been rejecting them, which is what two failing tests were actually catching. The fix was to teach the audit about WAL, not to weaken it.

3.3 Measured effect

configurationlease-grant latency
DELETE + EXTRA (original)8.697 ms
DELETE + NORMAL4.498 ms
DELETE + OFF0.054 ms
WAL + NORMAL (chosen)0.024 ms

That is roughly a 360× reduction on the lease path. WAL additionally removes reader/writer serialisation; the concurrency suite's wall time fell from 50 s to 12 s. The choice of normal over off is deliberate: it keeps the SQLite index crash-consistent without paying per-commit durability on a cache whose loss is already handled.

3.4 The decode claim, corrected

An earlier internal write-up reported this fix as a 4.8× decode recovery (∼12 → 58.1 tok/s). It is not, and the reason is worth recording as a measurement discipline rather than an apology.

Speculative decoding makes throughput a function of acceptance length:

tok/s = (acceptance_length * 7 + 1) / milliseconds_per_step

The original comparison ran its two arms against different prompt mixes with different acceptance lengths, with a page-cache flusher still running during part of it, and with a leftover benchmark container competing for the same engine. All three change tok/s without changing the engine. The controlled re-run, with the engine idle, the flusher stopped, and 8 repetitions per arm:

armdecodeper-step latencyacceptance
lock-scope fix reverted42.1 tok/s~83 ms/step0.35–0.61
lock-scope fix applied41.0 tok/s~83 ms/step0.35–0.61

Per-step latency is identical. There is no decode regression and there was no decode bug. For scale, the model publisher's own published figures imply about 118 ms/step at 0.959 acceptance and 125 ms/step at 0.341. Our ~83 ms/step is faster per step; the gap in headline tok/s between us and any other report is a difference in prompt mix and therefore in acceptance length, not in the engine.

The lesson is narrow and practical: report ms/step and acceptance length, not raw tok/s. Raw tok/s across differing prompts is not a comparable quantity.

3.5 Defect 3: a lookup budget that hung every real prompt

With defects 1 and 2 fixed the engine no longer died, but sessions still hung. Two further faults were found in the disk tier's lookup path, and they had to be separated because each masked the other. This is the first.

PERSIST_LOOKUP_KEYS_PER_STEP bounds how many new disk reservations the manager may charge in one scheduler step, answering RETRY for every chunk beyond that. vLLM's _maximal_prefix_lookup treats a single RETRY as "defer the whole lookup" and discards every hit already found in that scan:

case RETRY:
    defer_lookup = True       # does NOT break
...
return hit_count if not defer_lookup else None

The shipped value was 8. A real prompt needs far more than eight fresh reservations, so the scan returned None on essentially every pass and the request was deferred indefinitely.

Same build, same 8,171-token prompt, cold then repeatedbudget = 8 (shipped)budget = 2048

An 8,171-token prompt resolved to 74 chunks, about 110 tokens per chunk, which gives the sizing rule directly: the budget must be at least the chunk count of the longest prefix you intend to restore. For the 405k-token prompt measured safe in 4.7 that is ~3,700 chunks, so the value shipped here is 2048 (covering every context size in the matrix) and a deployment serving the full safe bound should use 4096. The old value of 8 did not merely under-perform: it made restores hang for any prompt longer than roughly 900 tokens.

3.6 Defect 4: the lookup gate could deadlock

Raising the budget fixed the hang for ordinary prompts but exposed a second, independent fault. The gate that apportions lookup turns advanced in exactly one place, on_schedule_end — and that hook only runs when the scheduler makes progress. A request deferred by the gate produces no batch, so the hook never runs and the turn never advances:

request's lookups all answered RETRY
  -> the request produces no batch
    -> the scheduler has nothing to run
      -> on_schedule_end is not called
        -> the turn never advances
          -> every later lookup is RETRY again

On the engine this presents as a healthy process with /health returning 200, no exception anywhere, and:

Engine 000: ... Running: 0 reqs, Waiting: 1 reqs, Deferred: 1 reqs,
             GPU KV cache usage: 0.0%, Prefix cache hit rate: 0.0%

The client hangs until it times out. It was reproducible on a cold prompt with nothing on the disk tier at all, which is what pointed at the gate rather than the store: a cold lookup should simply miss and end the scan.

The fix advances the gate on wall-clock as well as from the scheduler hook, through a single rotation helper used by both paths. One owner still receives its whole per-step key budget within one scan, so the throttle is unchanged; what changes is that the gate can no longer be stranded by a scheduler with nothing to do.

Test (tests/test_lookup_gate_liveness.py)Without the fixWith the fix
second owner admitted without the scheduler hookFAIL — "owner B was never admitted without on_schedule_end"pass
repeated retry always resolvesFAILpass
gate clears on degradeFAILpass

The tests never call on_schedule_end, reproducing a scheduler with no batch to run, and run in 0.12 s with no engine. Three of four fail on the reverted tree. The fourth is kept deliberately: it asserts that liveness was not bought by deleting the throttle, since a change that removed the budget would pass the other three and be wrong. Full package suite after both fixes: 254 passed.

The lesson, which cost several engine restarts. A throttling signal must not depend for its own release on the subsystem that the throttle stalls. RETRY was the right word for "later", but the only thing that could make it later was the work it had just blocked. Both of these defects were invisible in the counters: request hitching and hang both present as "deferred" and "load bytes zero", which is why the path tracing in 5.3 was needed to tell them apart.

4.1 What the shape says

  • Aggregate throughput saturates at about 73–75 tok/s from concurrency 2 onwards. A batch of two already reaches the ceiling; going to six adds nothing. The engine is saturated long before the request queue is.
  • Per-stream throughput halves as concurrency rises, from 39.6 to 21.1 tok/s. That is the expected trade: the same aggregate is spread over more streams. It also means per-stream latency is what you are choosing when you choose a concurrency level.
  • Concurrency above 4 is not real concurrency on this configuration. The engine's own occupancy telemetry recorded a maximum of 4 running requests throughout, because MAX_NUM_SEQS=4 caps the batch. The C5 and C6 rows therefore measure queueing behaviour, not wider parallelism, and their flat aggregate numbers confirm it. Raising this ceiling is a memory decision, not a scheduling one, and it competes with the KV pool.
  • Acceptance length varies by prompt, and that is the whole story of the tok/s spread. The accepted-per-drafted ratio here ranges 0.331–0.478, which at k=7 means roughly 3.3 to 4.3 tokens accepted per step. Different prompt mixes in other reports produce very different ratios, and therefore very different headline throughput, on identical hardware.
Configuration note. This standard bench was measured on the engine before the two load-path fixes in 3.5 and 3.6, i.e. with PERSIST_LOOKUP_KEYS_PER_STEP=8. That does not invalidate it — the bench salts every prompt uniquely to defeat prefix caching, so it exercises cold prefill and decode rather than the reuse path those fixes affect, and all 63 requests completed with zero failures and zero deferrals. It is flagged because a reader comparing this table against a run on the current configuration should know the configuration changed.
Measurement conditions, stated because they matter. The bench ran for 10 min 27 s. The endpoint is fronted by a gateway and can receive traffic that is not ours, so the run recorded both an occupancy sampler and the gateway's own request log. Over the 60-minute window ending with the run the gateway logged 23 requests to this model, and zero of them fell inside the measurement window: the numbers below are uncontended. The engine reported 208 occupancy samples, of which 100% had at least one request running and 77% had more than one, with a mean of 2.64 — all of it this bench, consistent with the wave structure. The sampler also recorded a hard ceiling of 4 concurrently running requests, which is the section 4.1 finding below.

4.2 Session matrix: method

Single-request throughput says little about how this deployment behaves for sessions, which is what the disk tier exists to serve. Four lanes were run against one engine, in the order below, on an otherwise idle node set. Every cell reports time-to-first-token, prompt and output token counts, wall time, speculative-decoding acceptance, and that cell's delta for every persistence counter. A timeout or a deferral is recorded as a failure in the timeouts column and never retried into the sample.

LaneWhat it measures
L1 cold ladderOne unique session per context size, nothing cached. Gives the prefill curve.
L2 warm ladderThe same session sent twice. Gives whatever reuse the stack actually delivers.
L3 concurrentN distinct sessions at C=1..4 at fixed context. Gives the concurrency cost.
L4 evictionUnique sessions until the GPU KV pool must evict, then re-request an early session while the engine is busy.
One measurement limitation, declared up front. This engine delivers a completion in a single burst at the end of the request: a 61-token response arrived as one content delta, 20 SSE events in total, at t=20.95 s. Per-stream decode rate therefore cannot be derived from inter-token timing, and every decode_measurable flag below reads false. What the timing is good for is prefill: with generation this short, time-to-first-token is effectively the prefill latency, and that is how prefill_tok_s is derived. Aggregate output tokens over wall time is also always valid. Both are reported; a fabricated decode rate is not.

4.6 L4 — eviction and busy-disk refill

This is the lane the disk tier exists for, and it is also the one that is hardest to run honestly, so the method and the shortfall are both stated before the numbers.

How much work eviction actually takes. The engine reports its own cache size at startup:

Available KV cache memory: 43.23 GiB
GPU KV cache size: 3,407,692 tokens, Maximum concurrency for 850,000 tokens per request: 4.01x

So forcing the GPU cache to evict requires inserting more than 3.4 million unique tokens. Measured aggregate insertion under C=4 concurrency is roughly 1,500 tokens/s, so the pool alone costs about 2,270 seconds of filling before any eviction can occur. Every attempt below is therefore time-boxed, and each one is reported with the fraction of the pool it actually reached rather than being presented as an eviction result it did not achieve.

The first two attempts ran their full budget with zero hangs and zero deferrals, so the shortfall was purely a matter of wall time. The third was sized from that arithmetic and crossed the pool, inserting 113% of the cache in unique tokens across 674 sessions in 2,713 s. That is the condition this lane existed to create: the GPU prefix cache was genuinely forced to evict.

Eviction pressure changes nothing. With the cache under real forced eviction and 4,040,069 external prefix queries issued, the tier answered zero of them and transferred zero bytes. This is the single most decisive result in the report, because it removes the last benign explanation. The tier does not fail to serve because the GPU cache never gave it a chance. It is given 4 million chances under exactly the pressure it was designed for, and it does not serve.

Read that as the operational answer to "how does the tier behave under busy concurrent sessions": it is consulted 2.33 million times, answers 332 of them, and transfers nothing. The hit rate is 0.014%. The refill after the fill completed in 3.07 s against a 4.10 s cold baseline, which is the GPU cache doing the work — not the tier.

The 1.9% GPU prefix-cache hit rate is the other half of the picture and is not a defect: every session in the fill is deliberately unique, so a low hit rate is the intended condition. It is quoted to show that the caching machinery was live and being exercised while the tier failed to contribute.

The honest summary of L4. The tier sustains the lookup load — 4.04M external queries across 674 concurrent sessions, with zero hangs — and serves none of it, including under genuine forced eviction at 113% of the KV pool. The eviction lane is therefore complete, and its answer is negative and unambiguous. What it cannot tell you is why: section 5.3 shows by path tracing that vLLM never reaches prepare_load at all, so the tier is never asked to serve. That is where the remaining work is, and further benchmarking of this lane would add nothing until it is fixed.

5 · Persistence: what works, what does not

This section is deliberately separated from the throughput results because the honest summary of the tier at the end of this campaign is asymmetric: the write path works well, and the restore path does not yet fire.

5.1 The eviction and refill experiment

The tier's own quota is 1 TB with watermarks at 900 GB and 800 GB, so its eviction path cannot be reached by volume at test scale. The reachable and far more important direction is the GPU side: force the GPU prefix cache to let go of a session, then ask for it again and see who serves it — the GPU cache, the disk tier, or a full recompute.

The probe does exactly that with one prompt. Phase 0 sends a unique ~5.3k-token prompt cold. Phase 1 immediately re-sends the identical prompt, which is the simplest possible expression of the tier's entire purpose: the prefix is already in the GPU cache, and it has just been written to disk, so this request should be trivially cheap from either tier.

=== phase 0: cold prefill of the target prompt ===
  cold: 2.84 s  prompt_tokens=5279  prefix_hits=0  store_B=182949888
=== phase 1: immediate repeat (should be served from a cache) ===

Phase 1 never returned. The request entered the deferred state and stayed there. The engine's own counters at capture:

The deferred state is the specific one to understand. The request is not waiting for a GPU slot — capacity-waiting is zero and nothing is running. It is waiting for a KV transfer that is never issued. Nothing is logged as an error, nothing is returned to the client, and the request does not time out. It simply never completes.

The flood phase of the experiment was abandoned rather than completed, because each deferred request occupies its worker for the full client timeout: at four workers the flood could not have advanced. The finding was already decisive at the first repeat, which is the cheapest possible case.

Why this matters more than the throughput numbers. Parking a session on disk and resuming it is the entire purpose of this tier. The write path performs correctly, and the persisted objects are real and durable across restarts (5.2). But the read path does not merely underperform: storing a prefix makes the next request for that prefix hang indefinitely with no error. An operator would reasonably conclude from the metrics that the cache had a low hit rate, while the clients would be stuck. That combination — a silent client hang behind a metric that reads 0.0% — is the single most important finding in this report, and it is why the counters described in 5.4 exist. Section 5.3 gives the verdict those counters produced.

5.3 The restore path does not fire, and the failure mode is a hang

Against a store holding 2,302 objects, the engine reported:

The write path and the read path therefore disagree with each other. Data lands on disk and survives a restart, and the same engine cannot get it back. The failure is not silent in the sense of being invisible: it is visible as a permanently deferred request that never completes and never errors. For an operator this is the worst shape a failure can take, because the client hangs rather than being told to retry.

Mechanism: found completely, and then never transferred

The two new counters were added precisely to decide this, then deployed to all four ranks and exercised against a fresh engine. One unique 8,171-token prompt, sent cold and then immediately repeated, gives an unambiguous answer.

1 — cold4.6 s10252,797,952 (112 stores)000

The first pass stored the prompt as 112 chunks. The second pass found 112 chunks. The prefix is therefore not partially cached, not mis-keyed and not slow: the tier holds the entire prefix and returns all of it, within two seconds. Sampling the counters every two seconds shows that plainly — the hit count rises 76 → 112 and then stops, because there is nothing left to find:

t=  0.0s  queries=  34916  hits= 76  load_B=0  deferred=0  running=0
t=  2.0s  queries=  35708  hits=112  load_B=0  deferred=1  running=0

t=239.0s  queries= 71028  hits=112  load_B=0  deferred=1  running=0
RESULT: 240.1s -> TimeoutError: timed out

Four things follow, and they are the whole diagnosis.

  • The store and the lookup are both correct. 112 of 112 chunks matched. This excludes the store, the keying, the geometry and the eviction policy as causes, and it excludes the "consulted and missed" reading of the 0.0% hit rate.
  • The transfer is never issued. Zero load bytes for the full 240 seconds. The prefix is located and then discarded.
  • The request is deferred, not failing. deferred = 1 continuously from t=2 s to t=240 s. Nothing errors server-side, nothing returns, nothing times out server-side. Only the client times out.
  • The engine burns CPU retrying. Lookups climb at roughly 880/s for the first 76 seconds, then collapse to about 4/s — a retry loop that is eventually throttled but never resolved. 36,137 lookups were issued for a prefix that had been fully located at t=2 s, and external_prefix_cache_queries advanced by 11,280 while external_prefix_cache_hits stayed at 0 — correct accounting, because vLLM counts a hit only when a transfer actually supplies tokens.

So the defect sits downstream of the lookup: between a resolved hit and the transfer that should follow it. That is a narrower and much better-supported statement than "the restore path does not fire", and it came from adding the counters rather than from reading more code.

A hypothesis that was tested and rejected

One plausible cause was tested and eliminated, and the rejection is recorded because it is worth as much as the conclusion. vLLM's scan discards the entire hit count if any chunk returns RETRY, and our lease-validity check returns False — without queueing a renewal — when the coordinator reports no deadline. If a freshly granted lease had no deadline, every reserved chunk would RETRY until a renewal landed and the scan could never converge.

A stub modelling that coordinator reproduced the observed shape exactly: 673 scheduler steps to converge instead of 10, with one renewal per chunk; and with the deadline seeded at reservation time, back to 10 steps with zero renewals.

The hypothesis is wrong, and reading the real coordinator rather than the model of it is what showed that. The reservation path already sets the lease deadline at grant time, so a fresh reservation is immediately valid for its full window. No change was made to the lease-validation, deadline or renewal code on the strength of that stub. This is the third hypothesis in this campaign that a stub could support and the real source refuted, which is the argument for keeping both.

The remaining site is therefore the transfer itself: whether the loader is invoked for a resolved hit, and why the resulting job never completes. The next step is a debug trace at that boundary, not further reading of the lookup path.

Path tracing: the load lifecycle is never entered

The conclusions above were reached by inference from counters. They were then tested directly by adding one bounded, static-code notice at each boundary of the load lifecycle, on both the manager and the worker-side transfer pump, and deploying it to all four ranks. A boundary that is never reached simply never logs, which turns "where does it stop?" into a list of which boundaries were visited.

After a cold store followed by a repeat, the boundaries reached were:

Three things follow, and the third is the useful one.

  • It is not the store and not the lookup. The tier is reached and returns leases.
  • It is not the transfer pump. The pump never refuses anything because it is never asked. The nine silent return False paths in its admission check were a plausible suspect, and they are now excluded by instrument rather than by argument — each of them was also converted into a named, counted rejection so that a future refusal is visible instead of silent.
  • The stop is upstream of prepare_load. vLLM never asks the manager to stage a load at all, so kv_offload_load_bytes_total is zero because no load was ever prepared. It is not a prepared load that stalled.

That is a materially better statement than "the restore path does not fire", and it was worth the instrument: three earlier hypotheses in this campaign looked convincing and were wrong, and the only thing that separated them from the truth was a boundary that either logs or does not.

5.4 Cache-hit accounting: already correct, but invisible and genuinely missing

An initial reading of this deployment concluded that a disk-cache hit was not being counted as a cache hit at all. That was wrong, and the correction matters. vLLM does distinguish the two sources of reuse, and it already routes offload-tier hits into their own accounting:

Engine 000: Avg prompt throughput: ... Running: 0 reqs, Waiting: 1 reqs, Deferred: 1 reqs,
GPU KV cache usage: 0.0%, Prefix cache hit rate: 86.6%, External prefix cache hit rate: 0.0%

The two numbers are deliberately separate. Prefix cache hit rate is the GPU-resident block cache. External prefix cache hit rate is the offload tier, and it is fed by a complete chain that already exists: the tier's manager reports a lookup hit, the scheduler converts it through get_num_new_matched_tokens into num_external_computed_tokens, and the connector records it into vllm:external_prefix_cache_hits_total — the same counter that drives the log line. A disk block is not, and should not be, part of vllm:prefix_cache_hits_total, which is GPU-only by design.

So a printed 0.0% is not an accounting gap but a measurement: the tier was consulted and no query was served. That is independent confirmation of the defect above, arrived at from a different direction — and the reproduction in 5.3 sharpens it further, showing that the tier is consulted, does match, and still is not served.

Two real gaps remained, and both are now closed and verified on the live engine.

  1. The client could not see cache reuse at all. The API response contained no usage.prompt_tokens_details object, because --enable-prompt-tokens-details defaults to false. This was never an offload-accounting problem: the underlying num_cached_tokens is already computed as local plus external, so a disk-served prefix would appear in cached_tokens — it was simply never serialised. The launcher now enables the flag, and the field is confirmed present on the wire: "prompt_tokens_details": {"cached_tokens": 0, "created_cache_tokens": 0, ...}.
  2. An operator could not tell "consulted and missed" from "found but deferred". With the rate pinned at zero the two failures are indistinguishable, and they call for opposite responses. Two counters are now emitted through vLLM's sanctioned build_metric_definitions() extension point, deployed to all four ranks and confirmed live at /metrics: vllm:kv_offload_tiering_chunk_queries_total and vllm:kv_offload_tiering_chunk_hits_total, both labelled tier="disk".
disk queriesdisk hitsReadingNext step

>00the tier is consulted and does not hold (or cannot validate) the prefixinvestigate keying, geometry and eviction
>0>0, external hits stay 0the tier holds it and the lookup returns "retry" — the stuck deferral. This is our case.investigate staging and admission (O1, O3)

The counters are increments only. They change no hit, miss, admission or eviction decision: the point is to make the existing decision legible, not to alter it. They were worth their cost for a concrete reason — the third row is the one they identified, and it is not the row anyone had assumed.

6 · Method: finding these without paying for engine startups

The expensive resource in this campaign was not GPU time, it was the roughly 7-minute engine restart. Almost every hypothesis was therefore tested against a stub first, and the engine was used only to confirm. That split is worth describing because it is what made the schedule feasible.

6.1 What stubs settled outright

Both quantities behind the request cap are closed-form functions of the configuration, so they were evaluated in a single line of Python. That is a stub harness for the engine's memory planner. It is exact for profile-time reservations, it costs nothing, and its real value was deciding which lever mattered — VLLM_SPARSE_INDEXER_MAX_LOGITS_MB, not MAX_MODEL_LEN — before any launch was spent.

The same discipline produced the durability fix. A concurrency runner with dummy geometry and a fake coordinator exercises the real store in well under a second with no engine, no network and no GPU. That is where the 8.697 ms lease grant was found and where the four journal/synchronous combinations were measured. The package's own test suite (99 tests) and a concurrency suite of 181–184 tests, of which 164–167 pass with 17 failures all traceable to known open defects and zero hangs, both run without an engine.

Import cost for the whole persistence package, seven modules, is 0.07 s; 0.70 s including a container start. A test cycle that costs under a second changes how willing you are to test a hypothesis.

6.2 What stubs cannot fake

A driver-level NV_ERR_NO_MEMORY is not reproducible in a stub. It depends on a 128 GiB unified pool carrying a roughly 101 GiB carve-out, and on the caching allocator's reservation behaviour. The existence and the size of the cap had to be measured on a real engine. Stubs narrowed the search space; the engine only confirmed it.

6.3 The instruments that paid for themselves

InstrumentWhat it gave

Two of these — the memory sampler and the usage-based decode bench — cost nothing to run and together produced the two most valuable measurements of the effort. The next instrument, if a further multi-hundred-megabyte reservation needs attributing, is torch.cuda.memory._record_memory_history() with _dump_snapshot() around one failing request, which gives every allocation with its Python stack.

6.4 Benchmark hygiene rules adopted

  • Stop the page-cache flusher after /health returns 200 and before measuring. Leaving it running moved a controlled measurement from 41 to 13–17 tok/s.
  • Assert num_requests_running == 0 and num_requests_waiting == 0 first, and check for leftover benchmark containers.
  • Self-limit every runner with timeout N docker run --rm --name ... so a stuck probe cannot silently compete with the next measurement.
  • Warm up, then repeat, and report the spread. One arm at a time on a TP4 engine.
  • Report ms/step and acceptance, never bare tok/s across differing prompts.

7.1 Limitations of the measurements in this report

  • All throughput figures are single-engine point measurements on one TP4 deployment, not population estimates. Prompt mix determines speculative-decoding acceptance and therefore tok/s.
  • Speculative-decoding acceptance in this deployment has been observed from 0.341 to 0.959 depending on prompt type, which is a wider range than any performance claim here.
  • The published comparison figures quoted for scale come from a different hardware configuration and a different prompt set; they are context, not a controlled head-to-head.
  • Eviction was reached, but only just. The KV pool is 3,407,692 tokens; the successful run inserted 3,851,236 unique tokens, 113% of it, across 674 sessions and 2,713 s. That is enough to force LRU eviction but not enough to characterise a steady state under sustained overflow, and the fill is a single time-boxed episode rather than a soak. The negative result is solid; a throughput-under-sustained-eviction curve is not measured.
  • The disk tier's own quota is 1 TB with high/low watermarks at 900 GB and 800 GB, so its eviction path is not reachable by volume at test scale. What is testable is GPU-side eviction followed by a refill attempt, which is what section 4 exercises.
  • No RDMA is claimed. NCCL ran with NCCL_IB_DISABLE=1; the presence of a capable interconnect is not evidence that RDMA was used.

9 · Reproducing

9.1 Confirm the request cap yourself

Both terms of the cap are closed-form in the configuration, so the whole diagnosis can be checked without a GPU:

worst_decode_tokens = min(MAX_NUM_SEQS * (num_spec + 1), MAX_NUM_BATCHED_TOKENS)
decode_logits_elems = worst_decode_tokens * max_model_len * 4
prefill_cap_elems   = VLLM_SPARSE_INDEXER_MAX_LOGITS_MB * 1024 * 1024
reserved_bytes      = max(decode_logits_elems, prefill_cap_elems)

If the second term wins, the environment variable is your lever and max_model_len is not. Then confirm on the engine with the memory sampler, and confirm the cause rather than the symptom:

# 1 Hz unified-memory sampler on every rank, while ascending prompt sizes
free -m                      # watch MemAvailable, not just the container
sudo dmesg -T | grep -c NV_ERR_NO_MEMORY
docker inspect <engine> --format '{{.State.ExitCode}} {{.State.OOMKilled}}'

An exit code of 0 with OOMKilled=false alongside a rising NVRM count is the signature. Do not trust the exit code.

9.2 Confirm the durability cost yourself

This one needs no engine and no GPU at all. Run the store against dummy data and time a lease grant under each journal/synchronous combination:

DELETE + EXTRA    8.697 ms   <- the default, and the defect
DELETE + NORMAL   4.498 ms
DELETE + OFF      0.054 ms
WAL    + NORMAL   0.024 ms   <- chosen

Then prove from outside that the engine actually applied the policy. Use journal_mode, which is persistent; synchronous is per connection and a host-side probe will lie to you.

python3 bench_c1c6.py --url http://<head>:8000 --model <served-model-id> \

10.2 Reusable artifacts

  • Stub concurrency harness — runs the real store against dummy geometry and a fake coordinator in under a second. This is the tool that found the lease-fsync cost and the one worth copying into any similar tier.
  • 1 Hz unified-memory sampler — a few lines of shell, and the instrument that located the request cap. Copy it before you need it.
  • usage-based decode bench — counts emitted tokens from the API's own usage block, which is what exposed a 5–6× chunk-counting error.
  • Standard C1–C6 bench — decode throughput at concurrency 1 through 6 with unique salted prompts to defeat prefix caching, scraping speculative-decoding acceptance from /metrics.
  • Instrumented bench runner — wraps the standard bench with a pre-flight idle assertion, a metrics snapshot before and after, an occupancy sampler, and a record of any gateway traffic that shared the engine during the run.
  • Eviction and refill probe — warms a target prompt, floods the engine with unique long prompts to evict it from the GPU KV pool, then re-requests it and classifies the serve path from TTFT and the load-bytes counters.

10.3 Two measurement traps worth reusing as warnings

  • A benchmark that cannot fail loudly will publish zeros. An early run of the standard bench reported 0.0 tok/s for all 63 requests and still exited 0, because the model id was wrong and every request returned HTTP 404 into a handler that counted failures without printing them. The fix is one line that prints the first failure reason. Any harness that reports throughput should refuse to report success when every request failed.
  • Two privileged-view traps produced confident wrong answers. An unprivileged du reported a 7 GB store as 8 KB because the rank directory is root-owned inside the container; and a host-side PRAGMA synchronous probe reports the probe's own default, not the engine's policy, because that pragma is per connection. Only journal_mode is persistent and therefore provable from outside.
