The write-behind disk KV tier: zero-tax persistence for GLM-5.3-Flash

GLM-5.3-Flash EXL3 4bpw at TP4 on 4× DGX Spark (GB10), DFlash2 speculative decoding, with a node-local disk KV tier rebuilt as a write-behind cache: stores happen only when the GPU prefix cache evicts, reads are RAM-first with a size gate, and the whole tier is invisible to business-as-usual request latency. Measured end to end: zero store tax, decode at parity, floods absorbed with 36× less write amplification, and session restores 2.7× faster than the eager design it replaces.
GLM-5.3-Flash 320B MoE EXL3 TR3 4bpw 4× DGX Spark (GB10) vLLM TP=4, 121.7 GiB UMA/node DFlash2 k=7 write-behind disk KV tier 2026-09-12

Executive summary

This deployment serves GLM-5.3-Flash (320B MoE) on four DGX Spark nodes with a no-tax disk persistence tier: a write-behind cache that adds ~6.9M tokens of addressable session context (3.39M in GPU + ~3.5M token-equivalents on disk) while leaving business-as-usual latency indistinguishable from running with persistence off. The journey from heavy tax to no tax

Eager persistence taxed everything: stores on the request path, responses held for the store drain, synchronous all-rank admission RPCs — measured −11…−38% prefill and −37% decode at 256k, and 36× write amplification in floods. The redesign kept the lookup/restore path and changed the store policy to write-behind, then removed the residual costs one by one, each measured: (0009) stores only on GPU-cache eviction, at background priority, with demand-aware holding — zero store bytes on any request path; the R3 size gate skips small prompts; (0010) an in-RAM durable-key index plus in-process local dispatch took the lookup-scan tax from −22% to ~0% at 64k; (0011) the pressure gate makes an idle engine write nothing (0 bytes, census-verified); (0012) the idle-time staleness flusher gives durable cold sessions without any memory pressure, running only on decode-free steps. What remains is the honest residual: under a full pool, bounded background copies cost ~5% of decode — the price of the restores they enable.

1 · The two designs, and why write-behind wins

The first version of this tier stored eagerly: every newly-computed chunk was offered to the disk on the request path, responses were held until the store frontier drained, and admissions were synchronous all-rank RPCs. It worked — the tier served 6,912–16,128-token restores and survived floods — but it taxed exactly the requests it should protect, and it amplified writes 36× beyond what eviction semantics require.

The write-behind redesign keeps the lookup/restore path and changes only the store policy, as one endpoint of a dirty-ratio dial (evict-only ↔ eager):

eager (previous)write-behind evict-only (this report)
What gets storedevery newly-computed chunk, on the request pathonly chunks the GPU prefix cache evicts, copied at background priority
Response pathheld until the store frontier drainsuntouched — no hold, no gate
Allocation safetyfrontier liveness bound; allocation declines under flood (228 in the test flood)demand-aware deferred free: holds release under free-queue pressure; 11 declines, zero stalls
Readsidentical: RAM-first; the connector is consulted only beyond the GPU prefix-cache boundary; a configurable size gate (PERSIST_MIN_DISK_LOOKUP_TOKENS, 32,768) skips the disk entirely for small prompts

Engineering note for reproduction: the mode is PERSIST_STORE_MODE=eager|evict_only in the launch environment. Both modes ship in the same image; switching is one env edit and a restart, which is also how every A/B in this report was measured.

2 · Setup, briefly

GLM-5.3-Flash (320B MoE, 41B active) in EXL3 TR3 4bpw, tensor-parallel across four DGX Spark nodes (GB10, 121.7 GiB unified memory each), vLLM 0.28.1rc1.dev617 on a pinned upstream commit with a nine-patch persistence series (0001–0009) applied at image build and hash-pinned in a manifest. DFlash2 speculative decoding at k=7, --enforce-eager, fp8 KV cache, MAX_NUM_SEQS=4, max_num_batched_tokens=7168, prefix caching on with match-unit 4. The disk tier is per-rank ext4 on NVMe with a sqlite index, fronted by per-rank coordinators; engine and package run as one container per rank. Measurements were taken through the gateway on an otherwise quiet fleet, flusher stopped, DEBUG logging off; the two concurrency levels above 4 in the standard bench measure queueing, not parallelism (MAX_NUM_SEQS=4).

Where the tax went, for the record. Write-behind's first live version still paid −12% at 64k. Two package changes removed it, each independently verified: (0010) an in-RAM durable-key index so a lookup miss costs a set membership test instead of per-key sqlite reads and file stats on all four ranks (−12% → −5%); (0010b) in-process dispatch for the rank-local coordinator leg, removing one of four localhost HTTP RPCs per key (−5% → ~0%). Unit tests pin both: a counting connection wrapper proves zero index I/O on the fast negative; unroutable peer stubs prove the local leg never touches the wire.

4 · Session restore: the two sizes that matter

The disk tier exists for one number: how long a session that is not in RAM takes to resume. Two regimes matter — a working session evicted under load (§4.1) and a long agentic session restored after its context left the GPU pool entirely (§4.2).

4.1 The 9k-session restore under flood (measured, both modes)

Method: 400 unique 9k-token sessions at C=4 (3.6M tokens) against a 3.4M-token GPU pool, then a re-request of an early session. The flood forces the pool to evict; the re-request must come from disk.

Write-behind stores exactly what the GPU evicted, so the restore transfers a third of the bytes and finishes in 37% of the time. The flood itself runs 12% faster because nothing on the request path waits for storage.

4.1a · The pressure-gate smoke (patch 0011, 2026-09-13)

With eviction_store_high_watermark=300 (blocks; pool ≈1,472), an idle engine writes nothing — a full 8k+64k prefill/decode smoke run stored 0 bytes (disk census zero new objects), while prefill matched OFF (1,984 / 1,987 tok/s) and decode held 50–51 tok/s. Under a 120×9k flood with interleaved decode streams, decode measured 39.1 vs 41.0 tok/s idle (−4.6%) — the entire cost of persistence while the pool is full, copies active, and 1.08M flood tokens flow. That is the whole tax curve: zero when unpressured, ~5% under full pressure.

4.5 · The 400k practical maximum — and the baseline question

This fleet’s configured max_model_len is 850,000; the practical single-request ceiling is ~405k tokens, set by unified-memory allocation during prefill — the 400k smoke cell served 404,745 tokens cleanly while 850k is refused at admission. Crucially, this wall predates and is independent of the persistence tier: it is the four-node UMA budget at TP4 with --enforce-eager. The published baseline configuration this recipe extends (tonyd2wild’s 1M-KV TP4 playbook, same hardware, same eager-mode serving) presumably shares the same ceiling — but that has not been measured on the baseline, and the “1M” in its name suggests it may not have been exercised there either. Recommended follow-up: run the same 400k→850k ladder on a persistence-off baseline build to confirm the wall is identical; until then, quote ~400k as the per-request ceiling for this hardware regardless of persistence.

4.2 Large-session restore, the capture window, and the 990k question

Measured with the flood method (seed the session, flood 300 × 9k to force GPU eviction, re-request; step-driver keeps the scheduler stepping):

800k session, seed pass299.7 s423,936 the durable prefix (184 chunks, ~424k tokens) restored from disk mid-prefill; the remainder recomputed

The capture window — the measured boundary that decides whether a restore exists. Write-behind holds evicted blocks in a credit-bounded registry (eviction_hold_cap = 4096 blocks) while background copies drain at eviction_store_per_step = 8 keys per scheduler step. A 300 × 9k flood evicts far more blocks than the window holds: the lookup reason census after the flood reads reserve_none = 298,346 for the sessions' keys — the window closed before their eviction arrived, and they were freed unstored. This is not a defect; it is the dial the design names. Raise eviction_hold_cap (more held memory, wider window) or eviction_store_per_step (more copy bandwidth, faster drain) to persist larger working sets under flood — the right setting is a per-deployment measurement, and the census above is how you see it.

The 990k session, answered with measurements rather than invention. This fleet cannot even admit 990k (MAX_MODEL_LEN=850,000; measured ~405k single-request UMA cap), so no honest 990k restore number exists here. What the measurements support: restore is bytes-linear (~250–330 MB/s effective, first chunk computing immediately); the durable-prefix row above is a real 424k-token restore inside a live request; and under flood the binding constraint is the capture window, not bandwidth. For a deployment whose window is sized to the working set, an 800k session ≈ 18 GB ≈ 60–75 s to restore versus ~400–500 s to recompute — the ~6× shape the 9k and 424k measurements bracket. Extrapolated, labeled as such.

5 · Stability and the engineering underneath

  • Flood safety by construction. Write-behind holds evicted blocks out of the free queue while copying them; a watermark declines new holds and the drain proactively returns holds under allocation pressure. The first flood without that guard crashed the allocator; with it, 11 declines and zero stalls.
  • Failure injection (engine-free harness): rank death and restart, disk pressure, and rank flap suites pass on the package; the lookup/restore contracts they pin are unchanged by 0009–0010b.
  • Patch discipline: the engine series (0001–0009) is hash-pinned in a manifest with before/after hashes for every touched file; an AST-based test suite binds the patched scheduler's methods and runs them against fakes on pristine CI hosts (45 tests, green across the series).
  • Package tests: 114 pytest tests plus the new 0010 suites (10 durable-index tests, 7 local-dispatch tests) run engine-free.
