# BENCH — GLM-5.3-Flash EXL3 TP4, TTFT / prefill / decode / needle / concurrency (2026-09-10 AEST)

**Time box:** 20:44–21:44 AEST, plus a follow-up concurrency sweep at 21:40–21:46.
**Harness:** `/tmp/bench_lane.py` on node0 (stdlib, streaming, unique-per-seed prompts so nothing is
served from prefix cache). **Method:** TTFT is time to the first streamed token, so prefill =
prompt_tokens / TTFT only holds when the request is not queued. Decode = completion_tokens /
(total − TTFT). Failures are disclosed, never replaced by a fabricated cell.

Endpoint: engine `node0:8000` (`glm-5.3-flash-exl3`), config `MAX_MODEL_LEN=850000`,
`GPU_MEM_UTIL=0.85`, `MAX_NUM_SEQS=4`, `MAX_NUM_BATCHED_TOKENS=7168`, `KV_CACHE_DTYPE=fp8`,
`PREFIX_MATCH_UNIT=4`, DFlash2 spec decode (7 tokens), `PERSISTENCE=on`.

## 0. CORRECTION — every decode number in this file is undercounted ~5–6×

**Added 2026-09-11 AEST.** The harness counted **streamed SSE chunks** as completion tokens. With
DFlash2 speculative decoding each chunk carries several accepted tokens, so decode throughput here is
too low by the tokens-per-chunk factor. Measured directly against `usage.completion_tokens`:

| context | completion_tokens (usage) | SSE chunks | tokens/chunk | decode by usage | decode as reported here |
|---|---|---|---|---|---|
| 7.5k | 200 | 31 | 6.45 | **27.5 tok/s** | 4.3 |
| 30.8k | 200 | 39 | 5.13 | **13.3 tok/s** | 2.6 |

So read every "decode tok/s" column below as **÷ that factor** — the real figures are roughly
**13–28 tok/s**, not 7–12. Prefill, TTFT and needle results are unaffected (they never depended on the
chunk→token mapping).

Two further corrections from the same session:
- **The request cap is 83k–165k tokens, not 131k.** At ~82.7k tokens the prompt survives with
  persistence on; at ~165k the engine dies (NVRM `NV_ERR_NO_MEMORY`). My earlier prompt builder
  under-counted tokens by ~2.4×, so some "target" sizes in §2 were larger than labelled.
- **The crash is not caused by persistence.** An equivalent ladder with `PERSISTENCE=off` also ended in
  an NVRM OOM. See `FIX-PLAN-20260911.md` §C1.

**Concurrency ceiling: no hard limit was reached.** Every request succeeded at every level up to
C=8 (24/24 requests, zero failures). Above the configured `MAX_NUM_SEQS=4` the surplus merely
**queues**, and queueing is plainly visible in the TTFT spread: `max−min` TTFT grows from 4.1 s at
C=2 to 17 s at C=6 and 63 s at C=8, and mean TTFT rises 7.7 s (C=1) → 22.0 s (C=4) → 28.6 s (C=6) →
39.9 s (C=8).

**Throughput does not scale with concurrency.** Per-request decode stays ~9–12.5 tok/s at every
level, while *aggregate* decode rises only 3.90 → 4.92 → 4.88 → 5.62 → 6.06 → 4.96 tok/s
(C=1…8): about **1.55× at best (C=6)** and a regression at C=8. Aggregate prompt throughput is flat
at ~870–990 tok/s, and per-request prefill collapses from 1,063 tok/s (C=1) to 113–421 tok/s (C=8).
Read: the engine slices work between requests rather than batching it efficiently — consistent with
`--enforce-eager`, spec decode and chunked prefill (`MAX_NUM_BATCHED_TOKENS=7168`) on 4-node TP4.
The lane buys latency headroom from concurrency, not throughput.

Caveat: the C=1 @8,192 row was the first request after an engine reload (~1 min after `/health`), so
it is a cold-engine number and lower than the ladder rows at 4k/16k.

## 3. Ceilings

- **Context: 65,711 works; 131,072 kills the engine.** Practical ceiling is between **65k and 131k**
  — far below the configured `MAX_MODEL_LEN=850000` and the LiteLLM `max_input_tokens=240000` public
  cap. Not bisected (each probe costs a full engine reload).
- **Concurrency: no ceiling up to C=8**; `MAX_NUM_SEQS=4` is the point where latency (not
  correctness) starts to degrade, per §2 above.

## 4. Bugs

### 4.1 Harness builder tokenized a runaway prompt — FIXED

The first builder generated one ledger line per *target token* (~7× oversized), so its first sizing
pass tokenized a **2,291,367-token** string and posted it to `/tokenize`. Rebuilt by construction
from a measured chars-per-token, with a hard 900,000-token cap on anything that reaches the endpoint
and a shorter socket timeout. First pass now lands within ~0.1 % of target.

### 4.2 The lane does not survive a >65k prefill — OPEN, SERIOUS

Three outages in the hour, one signature:

```
[Thu Sep 10 20:46:21/27/35 2026] NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory
    [NV_ERR_NO_MEMORY] (0x00000051) returned from _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359
[Thu Sep 10 21:05:54/21:06:01/21:06:08 2026] (same)
[Thu Sep 10 21:23:32/41/50 2026]           (same)
```

Chain: a large-context prefill drives the GB10 **unified** memory past the NVIDIA driver's limit →
`NV_ERR_NO_MEMORY` → the engine shuts down → vLLM's API server receives SIGTERM
(`vllm/entrypoints/launchers/launcher.py:126-136` is the SIGINT/SIGTERM handler) and begins a
graceful stop. **It then hangs** at `Waiting for connections to close` because a client socket is
still open: PID 1 stays alive, `/health` returns nothing, and the container never exits. Recovery is
a manual `./start-tp4.sh down` then `up` (~7 minutes to reload).

**Concurrency is ruled out as the trigger.** The sweep in §2 pushed 8 simultaneous requests at 8k and
4 at 32k — 24 requests, zero failures, and the NVRM OOM counter did not move. The trigger is
single-request **context size**, not parallelism.

Also ruled out: container OOM (`OOMKilled=false`, exit 0), node guards/watchdogs/cron (none exist on
head or the Sparks), `systemd-oomd` (inactive), and a `docker stop` (no dockerd journal entry).

**Prime suspect:** the persistence budgets are large relative to a 128 GB UMA that already holds
~45 GiB of weights and ~56 GiB of KV: `staging_bytes = 4,294,967,296` (4 GB) and
`max_pending_bytes = 64,000,000,000` (64 GB). A 131k-token prefill allocates activation/workspace on
top of that. **The next test is the decisive one: run the same 131k prompt with `PERSISTENCE=off`.**
If it survives, the persistence staging/pending budgets are the lever (they are the only
non-default-tunable values in §3.11, and the private deployment runbook already marks them "conservative initial
limits, not results"). If it also dies with persistence off, the ceiling is the base prefill
workspace and belongs to the model/engine port.

Note the recipe's own floor-guard ban is relevant here: there is no memory ceiling or kill machinery
by design, so an over-large prefill has nothing stopping it from taking the whole node's UMA — which
is exactly what these three incidents show.
