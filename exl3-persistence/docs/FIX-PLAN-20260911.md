## Part B — 15 open defects, ranked, with proposed fixes

Ordered by value = (silent wrongness × likelihood) ÷ fix risk.

### B1 [HIGH] `RpcClient` default admission rejects healthy callers
- **Repro:** `MetadataServer(threads=16)` + one shared `RpcClient` (1 endpoint, defaults → `max_active=1`, `max_pending=4`); 8 barrier-synced threads call `client.call(0,"geometry")`. Observed: exactly 4 rejected `_Transient: "RPC submission capacity exhausted"` while 16 server threads idle.
- **Fix:** admit by queueing up to a bounded wait instead of failing immediately; or raise the default `max_pending` to `max_active * pool_size * k`; or expose the bound as a required config value so it is never an accident. Do **not** simply remove the bound (it exists to cap memory).
- **Risk:** low–medium (behavioural), needs a decision on back-pressure semantics.
- **Acceptance:** `test_conc_coordinator_http::test_shared_client_rejects_concurrent_callers_at_default_pending_bound` passes; no unbounded queue growth.

### B2 [HIGH] That rejection becomes spurious all-rank cache misses
- **Repro:** 2 local ranks, defaults, 8 threads × 8 **uncontended** distinct-key `reserve_store`+`release` → **32/64 return `None`**; raising `max_pending=64` → 0.
- **Fix:** in `RemoteCoordinator`, retry `_admit`-rejections (they are transient by definition) with bounded backoff, instead of treating the rank as failed and rolling back the reservation.
- **Risk:** low. **Acceptance:** the test passes; a killed rank still reports failure.

### B3 [HIGH] `RemoteCoordinator._reserve` holds the global lock across network I/O
- **Repro:** inject a 0.25 s delay into one rank's `renew`; thread A re-reserves its identity while the main thread reserves a *different* uncontended key → unrelated reservation blocked 0.268–0.282 s (vs <0.01 s).
- **Fix:** take the lock only to read/validate the ticket and to install the result; perform `renew()`/`fanout` outside it, then re-check under the lock (optimistic pattern).
- **Risk:** medium (concurrency correctness) — needs care around the identity map.

### B4 [MED] `ENFORCE_EAGER=1` — CUDA graphs disabled (see Part C2)
- **Fix plan:** A/B `ENFORCE_EAGER=0`, with a crash/timeout guard. Mia's published numbers are explicitly **with CUDA graphs**; ours are eager.

### B5 [MED] `invalidate()` then immediate rewrite refused for `grace_seconds` (default 60 s)
- **Repro:** `lease_seconds=30, grace_seconds=30`; commit `b"k"`, `invalidate`, then `reserve_write` the same key → `None`; after advancing a fake clock past grace + `collect()` → succeeds.
- **Fix:** make the duplicate guard state-aware (`state='C'` only) and handle the tombstone by retiring it under the new object's identity, or let a rewrite "supersede" a tombstone atomically.
- **Risk:** medium — must not let a live reader of the tombstone be served stale bytes.

### B6 [MED] Tombstoned objects count toward `max_objects`
- **Repro:** `max_objects=4, grace_seconds=30`; commit 4 keys, `invalidate()` all → all `exists()==False` but a fresh `reserve_write` → `None`.
- **Fix:** exclude `state='T'` rows from the `max_objects` count (they hold no live data), or count them against a separate tombstone budget.

### B7 [MED] `DiskTransferPump` over-admits under concurrent `submit_store`
- **Repro:** 8 threads × 250 submits, `rows=8, max_pending_keys=400`, `sys.setswitchinterval(1e-6)` → 402–406 admitted.
- **Fix:** make the capacity check and `self.pending_keys += n` one atomic section (the pump already has a lock for other fields).

### B8 [MED] `_Manager.lookup`/`prepare_store` over-admit
- **Repro:** `capacity=4`, 8 threads with a barrier inside the fake coordinator's `reserve_load`/`reserve_store` → 8 live reservations.
- **Fix:** reserve capacity before the RPC (pessimistic) or reconcile after (optimistic with rollback), never check-then-RPC-then-insert.

### B9 [MED] `LocalCoordinator` parses `key[-4:]` without `key_group`'s guard
- **Repro:** `coord.reserve_store(ns, b"\x00\x00\x00\x01", "o", (20,20))` returns a Ticket while `key_group` raises for the same key; a `str` key escapes as raw `TypeError`.
- **Fix:** route both through `geometry.key_group` and return `None` per the `CoordinatorProtocol` docstring.

### B10 [LOW/MED] `RpcClient` collapses five distinct failure causes into one message
- **Repro:** oversize response, gzip/non-JSON 200, missing `{"ok":true}`, ECONNREFUSED → all `_Transient: "RPC transport failed"`; oversize request and non-serialisable params both `_Permanent: "RPC request rejected"`.
- **Fix:** preserve the cause in the static message (still no endpoint/token leakage).

### B11–B15 [LOW / COSMETIC]
- `_row_done` called twice → `IndexError` / poisoned `free` deque (private API; add an idempotency guard).
- No-vLLM refusal is a raw `ModuleNotFoundError` (wrap in a domain error).
- ~20 k-deep nested JSON → 500 not 400 (`RecursionError` not caught).
- `layout_fingerprint` `int()`-coerces `[1]/[True]/["1"]` (unreachable via the validated census).
- Post-close `evict()`/`collect()` latch semantics — settled by `clear_failure()`.

## Part C — engine-level defects (the two you asked about)

### C1. The request cap: large-context prefill kills the engine

**What happens [measured]:** a sufficiently large single prompt drives the GB10 **unified** memory
past the NVIDIA driver's limit. The kernel logs

```
NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY] (0x00000051)
      returned from _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359
```

the engine shuts down through vLLM's SIGTERM handler (`entrypoints/launchers/launcher.py:126-136`),
exits **cleanly (code 0, `OOMKilled=false`)**, and then **hangs draining the client socket** — PID 1
stays alive, `/health` returns nothing, and the container needs a manual `down` + `up` (~7 min).

**Measured boundary [measured]:** with `PERSISTENCE=on`, **82.7k tokens survived** and **~165k killed
it**. The cap is therefore between those, far below the configured `MAX_MODEL_LEN=850000` (engine)
and the LiteLLM `max_input_tokens=240000` cap.

**Critical correction [strong signal]:** the crash is **NOT caused by persistence**. An
same-sized ladder with `PERSISTENCE=off` also ended in an NVRM OOM and engine death. Persistence
memory budgets (`staging_bytes` 4 GB, `max_pending_bytes` 64 GB) may *shift* the threshold but are not
the root cause.

**How to reproduce:**

```bash
# 1. ensure the engine is up, then warm it (the first request after boot is cold)
# 2. send a single prompt of N tokens with max_tokens=16 and watch for the death
ssh node0 'docker run --rm --cpus=4 --memory=8g --network=host \
  -v /tmp/probe_ab2.py:/probe.py:ro --entrypoint python3 <image> /probe.py on'
# 3. confirm the cause, not just the symptom:
ssh node0 'sudo dmesg -T | grep -c NV_ERR_NO_MEMORY'          # must increase
ssh node0 'docker inspect glm53-exl3-tp4-head --format "{{.State.ExitCode}} {{.State.OOMKilled}}"'
```
Bisect with a ladder (~83k → 110k → 130k → 165k), one prompt per step, `max_tokens=16`.

**Candidate causes, in the order worth testing:**
1. **Prefill activation/workspace at long context** — MLA + chunked prefill (`MAX_NUM_BATCHED_TOKENS=7168`) on a 128 GB UMA that already holds ~45 GiB of weights and ~56 GiB of KV. Most likely.
2. **`GLM53_INDEXER_WORKSPACE=rightsize`** — the sparse-indexer workspace is sized for `max_num_batched_tokens`; check it scales with context.
3. Persistence staging/write-back pressure *during* a long prefill (definitely not the sole cause, but may move the threshold).
4. The `--enforce-eager` scratch path (no CUDA graph memory pool reuse).

**Proposed fix path:** instrument first (see the profiler plan), then either bound the prefill
workspace or make the engine *refuse* an over-large prompt with a clean 400 instead of dying.
Given the standing ban on floor guards, the preferred shape is a **serve-side check** that rejects a
request whose token count exceeds the measured safe prefill bound (`--max-model-len` is currently
850k, roughly 5× the observed safe value — that mismatch is itself the bug to fix).

### C2. Decode speed: mostly a measurement artifact, then a real persistence penalty

**Correction [measured]:** the first bench counted **streamed SSE chunks** as tokens. With DFlash2
speculative decoding each chunk carries several accepted tokens, so it undercounted by ~5–6×:

| context | `completion_tokens` (usage) | SSE chunks | tokens/chunk | decode by usage | by chunk count |
|---|---|---|---|---|---|
| 7.5k | 200 | 31 | 6.45 | **27.5 tok/s** | 4.3 (what I first reported) |
| 30.8k | 200 | 39 | 5.13 | **13.3 tok/s** | 2.6 |

**Always measure decode from `usage.completion_tokens`** (`stream_options: {"include_usage": true}`),
or from `vllm:spec_decode_num_accepted_tokens_total` ÷ steps.

**Against the source's own numbers [measured vs published]:** Mia's upstream README states the
official numbers use **CUDA graphs** and reports Structured **65.1 tok/s** (0.959 accept / 6.71 per
step), Prose **27.1 tok/s** (0.341 / 2.39), long/mixed context **24–27 tok/s**. Our config sets
**`ENFORCE_EAGER=1`**, and measured acceptance length was 0.43–0.68 on ledger/prose prompts — i.e. the
prose regime, where Mia's own number is ~27 tok/s. So the honest reading is: **our decode is in the
right band for prose, and the gap is (a) prompt-type/acceptance regime and (b) eager mode**, not a
gross engine fault. The 222 tok/s / 318 tok/s figures in our docs are the **TrellisMX vendor's
numbers on 4× RTX PRO 6000 @300 W** — different hardware and quant, not a valid target.

**The real defect [strong signal]:** an A/B on the same prompt measured **77.2 tok/s with
`PERSISTENCE=off`** versus **10–14 tok/s with it on** — a **5–7× decode penalty**. The offload
connector performs per-step lookup/store work (`lookup_keys_per_step=8`, coordinator RPC,
`disk_io_threads=4`) on the decode critical path. That single number is the most valuable thing to
confirm, because it says the persistence tier currently costs more than it gives on short contexts.

**How to reproduce (clean, warmed A/B):**
```bash
# warm up first — the first request after boot measured ttft=108s once, which poisons any benchmark
# then 5 reps x 200 new tokens at a fixed ~8k prompt; report MEDIAN decode and accept_len
ssh node0 'docker run --rm --cpus=4 --memory=8g --network=host -v /tmp/probe_ab2.py:/probe.py:ro \
  --entrypoint python3 <image> /probe.py on'    # then repeat with PERSISTENCE=off
```
Compare **median** decode and acceptance length. Then test `ENFORCE_EAGER=0` as a third arm.

## Part D — suggested order of work

1. **Confirm C2's 77 vs 12 tok/s** with a warmed, median-of-5 A/B (cheapest, highest information).
2. **Fix B1–B3** (they turn silent cache loss into either success or an honest error) — all three are

3. **Instrument C1** (UMA timeline + `nvidia-smi` sampler during a bisect) and only then choose
   between bounding the workspace and rejecting over-large prompts.
4. **Test `ENFORCE_EAGER=0`** as a third arm of the decode A/B.
5. **Deploy** the Part A fixes by rebuilding the image, or run another cycle with the
   `PYTHONPATH=/pkg` overlay if no C/CUDA change is involved.
